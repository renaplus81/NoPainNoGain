# 社畜サバイバル(仮) 基本設計書
 
> 前提: 要件定義書.md の内容をもとに設計した。
 
## 1. 概念設計
 
### エンティティ一覧
 
| エンティティ | 説明 | 主な属性(案) |
|---|---|---|
| User | ゲーム利用者 | 利用者id(PK)、名前、パスワード、ユーザー登録日 |
| GamePlay | 一回のプレイの状況。 | ゲーム状況id(PK)、利用者id(FK)、ステータス(プレイ中/死亡/生存クリア) |
| Task | 利用者が持つ根回しタスク | タスクid(PK)、タスク名、利用者id(FK)、所要時間、理不尽レベル|
| TaskProgress | あるプレイの中であるタスクが完了したかどうかの記録 | ステータスid(PK)、ゲーム状況id(FK)、タスクid(FK)、タスクステータス(未完了/完了) |
| OvertimeLog | 残業の記録 | 残業記録id(PK)、タスクid(FK)、発生日、残業時間|
 
### 関連(リレーションシップ)
 
- User 1 ── 1 GamePlay (複数回プレイに対応)
- User 1 ── 多 Task (利用者の持つタスク)
- GamePlay 1 ── 多 TaskProgress
- Task 1 ── 多 TaskProgress
- Task 1 ── 多 OvertimeLog

### 設計上のポイント

- タスクの完了状況はタスク自体には持たせず、ステータス管理という中間テーブルに分離。同じタスクでもプレイごとに独立したステータスを持てるように
- ステータス管理には直接user.idを持たせない。(間接的関数従属になるため)

## 2. 論理設計
 
### 多対多の分解
 
- 対象の関連: タスク - ゲーム状況(同じユーザーが何回も新しい状態(タスクステータス)で遊び直せる)
  - 中間テーブル名:　ステータス管理(TaskProgress)
  - 中間テーブルが持つカラム:ステータスid(PK)、ゲーム状況id(FK)、タスクid(FK)、タスクステータス

### 主キーの整理
 
 
| テーブル名 | 主キー | 採番方法(自動採番) |
|---|---|---|
| 利用者 | 利用者id | 自動採番(autoincrement) |
| ゲームの状況 | ゲーム状況id | 自動採番(autoincrement) |
| タスク | タスクid | 自動採番(autoincrement) |
| ステータス管理 | ステータスid | 自動採番(autoincrement) |
| 残業記録 | 残業記録id | 自動採番(autoincrement) |
 
### 正規化チェック
 
- 確認結果:
- 繰り返しの列がないか(第1正規形): 1マスに1列。OK。
- 複合主キーの一部にしか依存しない列がないか(第2正規形): 全て単独主キーなのでOK。
- 主キーに間接的にしか依存しない列がないか(第3正規形): 間接的な関数従属なし。OK。
